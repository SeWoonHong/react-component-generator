# Commit

변경사항을 읽고, 리뷰하기 좋은 단위로 쪼개서, 컨벤션에 맞는 한국어 메시지로 커밋한다.

## 실행 모드

- **기본 (자동)**: 계획을 세운 뒤 묻지 않고 바로 커밋하고, 끝나면 결과를 보고한다.
- **`--confirm`**: 사용자가 `--confirm`을 붙이거나 "확인하고 커밋해줘", "먼저 보여줘"처럼 요청하면 커밋 전에 계획을 보여주고 승인을 받는다.

자동 모드여도 아래 경우에는 **멈추고 사용자에게 묻는다.** 의도를 추측해야 하거나 저장소 상태가 평소와 다른 상황이기 때문이다.

- 사용자가 일부만 스테이징해 두어서, 그것만 커밋할지 전부 커밋할지 알 수 없을 때
- 한 파일 안에 크고 성격이 전혀 다른 변경이 섞여 있어 나누는 방법을 정해야 할 때
- 머지·리베이스 충돌이 진행 중이거나 detached HEAD 상태일 때

## 1. 변경사항 분석

먼저 상태를 확인한다.

```bash
git rev-parse --is-inside-work-tree   # git 저장소가 아니면 중단하고 사용자에게 알린다
git status --short
git diff --stat
git diff            # 스테이징 안 된 변경
git diff --cached   # 이미 스테이징된 변경
git log --oneline -10   # 기존 메시지 스타일 참고
```

- 새로 추가된(untracked) 파일은 `git status`에서 확인하고, 필요하면 내용을 직접 읽는다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

### 커밋하면 안 되는 파일

아래가 보이면 커밋 대상에서 빼고, 마지막 보고에서 무엇을 왜 뺐는지 알린다. 자동 모드에서도 절대 커밋하지 않는다.

- 비밀 정보: `.env`, `*.pem`, `*.key`, 자격 증명·토큰이 들어간 파일, diff 안의 API 키 문자열
- 빌드 산출물·의존성: `dist/`, `build/`, `node_modules/`, `coverage/`
- 개인 환경 파일: `.DS_Store`, 에디터 설정, 로컬 로그

`.gitignore`에 없어서 보이는 것이라면 `.gitignore` 추가를 보고에서 제안한다. 자동 모드에서 `.gitignore`를 임의로 고치지는 않는다.

## 2. 논리적 단위로 분류

하나의 커밋은 **하나의 이유로 바뀐 변경**만 담는다. 이렇게 나눈다.

- 기능 추가, 버그 수정, 리팩터링, 설정·의존성 변경은 서로 다른 커밋으로 나눈다.
- 같은 기능을 위한 코드·스타일·테스트는 한 커밋에 함께 둔다. 파일 종류별로 쪼개지 않는다.
- 한 파일 안에 성격이 다른 변경이 섞여 있어도 대개는 그 파일의 주된 목적에 맞는 커밋에 함께 넣는다. 섞인 변경이 둘 다 크고 성격이 전혀 달라 한 커밋으로 묶으면 리뷰가 어려울 때만 사용자에게 묻는다. (`git add -p` 같은 대화형 플래그는 쓸 수 없다.)
- 변경이 작고 한 가지 목적이면 굳이 나누지 않는다. 과하게 쪼개지 않는다.

순서는 의존 관계를 따른다. 예: `chore`(의존성 추가) → `feat`(그 의존성을 쓰는 기능).

## 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 쓰는 경우 |
|------|-----------|
| `feat` | 사용자가 체감하는 기능 추가·변경 (UI 개편 포함) |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 구조·가독성 개선 |
| `chore` | 빌드·설정·의존성·스킬·문서 등 앱 동작과 무관한 작업 |

요약 줄 규칙:

- 한국어, 50자 안팎, 마침표 없이 끝낸다.
- "무엇을 왜"가 드러나게, 명사형 또는 "~추가", "~수정" 같은 간결한 형태로 쓴다.
  - 좋음: `feat: 레트로 프린터 테마로 메인 화면 개편`
  - 좋음: `fix: 빈 프롬프트로 생성 요청이 나가던 문제 수정`
  - 나쁨: `feat: 수정`, `fix: 버그 고침`, `chore: 여러 파일 업데이트`

본문은 요약만으로 이유가 드러나지 않을 때만 쓴다. 72자 안팎에서 줄바꿈하고, 무엇이 바뀌었는지보다 **왜** 바꿨는지를 적는다.

세션에서 커밋 서명(Co-Authored-By 등) 안내가 주어졌다면 메시지 끝에 그대로 붙인다.

## 4. 커밋

### 자동 모드 (기본)

계획대로 바로 커밋한다. 묻지 않는다.

### `--confirm` 모드

커밋 전에 계획을 한 번에 보여주고 승인을 받는다.

```
커밋 계획 (2개)

1) feat: 레트로 프린터 테마로 메인 화면 개편
   - src/App.tsx, src/App.css, src/index.css
   - src/components/*.tsx

2) chore: commit 스킬 추가
   - .claude/skills/commit/SKILL.md

제외: .env (비밀 정보)

이대로 커밋할까요? 메시지나 묶음을 바꾸고 싶으면 말씀해 주세요.
```

사용자가 명확히 승인한 뒤에만 실행한다. 수정 요청이 오면 계획을 고쳐 다시 보여준다.

### 공통 실행 규칙

- 파일은 이름을 지정해 스테이징한다. `git add -A`, `git add .`는 쓰지 않는다.
- 커밋마다 스테이징 직후 `git diff --cached --name-only`로 의도한 파일만 올라갔는지 확인한다. 제외 대상 파일이 섞여 있으면 `git restore --staged <파일>`로 내리고 진행한다.
- 여러 줄 메시지는 HEREDOC으로 넘긴다.

```bash
git add src/App.tsx src/App.css
git commit -m "$(cat <<'EOF'
feat: 레트로 프린터 테마로 메인 화면 개편

생성 결과를 연속 용지 형태로 보여주어 새 결과가 어디에 나오는지
한눈에 알 수 있게 했다.
EOF
)"
```

## 하지 않는 것

- `git push`, PR 생성 (사용자가 따로 요청할 때만)
- `--amend`, `rebase`, `reset --hard`, `--no-verify` 등 기록을 바꾸거나 훅을 건너뛰는 작업
- git 설정(`user.name`, `user.email` 등) 변경

pre-commit 훅이 실패하면 출력 그대로 보여주고 원인을 고친 뒤 **새 커밋**으로 다시 시도한다. 훅을 우회하지 않는다. 원인을 고치려면 코드 수정이 필요한 경우, 자동 모드라도 수정 없이 멈추고 실패 내용을 보고한다.

## 마무리

커밋이 끝나면 아래를 보고한다. 자동 모드에서는 이 보고가 사용자가 결과를 확인하는 유일한 지점이므로 빠짐없이 적는다.

- `git log --oneline -n <커밋 수>` 결과
- 커밋별 포함 파일
- 제외한 파일과 이유 (비밀 정보, 빌드 산출물 등)
- 남은 미커밋 변경

결과가 마음에 들지 않을 때를 위해 되돌리는 방법을 한 줄로 덧붙인다: `git reset --soft HEAD~<커밋 수>` (커밋만 취소되고 변경 내용은 그대로 남는다).
